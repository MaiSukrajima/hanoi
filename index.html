02 / THINK RECURSIVELY

只管这一层，其余交给下一层。

递归不是把步骤背下来，而是先给函数一个明确承诺：
它能解决什么问题，又在什么时候停止？[2]

hanoi(n, src, aux, dst)
n 圆盘数src 起点aux 辅助dst 终点

函数的承诺：借助 aux，把 src 顶部的 n 枚圆盘合法地搬到 dst。每次调用都遵守同一个承诺，改变的只是规模和三根柱子的角色。

以 3 枚圆盘为例：先解决 2 枚圆盘的问题。图中是第一阶段全部完成后的状态。这里看似“整摞搬走”，实际仍要通过递归，一枚一枚移动。

01 / 为什么不会一直拆下去？

每次调用都让 n 减 1，最终来到 n = 1。这时没有更小的圆盘要处理，直接移动并返回。这就是终止条件（base case）。

“问题变小”还不够：必须保证沿着合法输入，真的能到达终止条件。本页的移动函数要求 n 为正整数；完整示例在入口处校验。

1定义要解决的问题2找到最小情况3每次接近最小情况

02 / “递”下去以后，怎么“归”来？

父函数不是消失了，而是暂停在调用语句处。子函数返回后，父函数接着执行下一行。每次调用拥有独立参数；同名的 n 不是同一个变量。

hanoi(2, A, B, C) // 暂停
↳ hanoi(1, A, C, B)
移动 1：A → B
↰ 返回到父调用
继续：移动 2，A → C；再调用另一子问题
03 / FROM IDEA TO CODE

三行策略，写成可运行的代码。

Python、JavaScript 与 C++ 使用相同的参数顺序。
复制整段示例即可运行；输入固定为 n = 3。

def move(disk, src, dst):
    print(f"移动圆盘 {disk}: {src} → {dst}")

def hanoi(n, src, aux, dst):
    if n == 1:                       # 最小问题
        move(1, src, dst)
        return
    hanoi(n - 1, src, dst, aux)       # 先腾空
    move(n, src, dst)                # 再搬大盘
    hanoi(n - 1, aux, src, dst)       # 最后归位

def solve(n):
    if type(n) is not int or n < 1:
        raise ValueError("n 必须是正整数")
    hanoi(n, "A", "B", "C")

solve(3)

注意参数的“换位”

A、B、C 是固定的柱子；src、aux、dst 是本次调用赋予它们的角色。

  • ①第一次递归，原目标柱变辅助柱，原辅助柱变目标柱。
  • ②中间只搬当前层最大的圆盘，移动方向是 src → dst。
  • ③第二次递归，原辅助柱变起点，原起点变辅助柱。
结果 / n = 3

04 / THE COST OF RECURSION

代码很短，工作量却可能很大。

递归 ≠ 高效的保证

两次规模为 n−1 的子问题，加一次大盘移动：[3]

T(n) = 2T(n−1) + 1
= 2ⁿ − 1T(1) = 1；T(n) 表示最少移动次数。

为什么已经是最少？最大盘第一次移动前，必须先把 n−1 枚小盘完整搬到另一根柱子，至少 T(n−1) 步。最大盘最后一次移到 C 后，小盘仍在别处，还需至少 T(n−1) 步搬到 C。再加上至少一次大盘移动，下界就是 2T(n−1)+1；三阶段策略恰好达到它。

输出全部移动的时间Θ(2ⁿ)
递归调用栈空间O(n)

05 / BEYOND THE PUZZLE

现实里，我们到底在用什么？

值得带走的，是“同类子问题 + 明确边界 + 返回合并”的思想，而不是照搬三根柱子的规则。

把“类比”与“应用”分清。堆放货物能帮助理解约束与依赖；下面列出的文件遍历、物料清单和网页树，则是真实软件中的递归结构或递归查询场景。它们并不直接运行汉诺塔的搬盘算法。[4][5][6]

真实 API · Python os.walk

统计一个文件夹，连同它的文件夹。

备份程序需要找到所有待备份文件；空间统计工具需要累计每个文件的大小。目录内部仍然可以是目录，天然形成了同类子问题。Python 的 os.walk 提供目录树遍历能力。[4]

同类子问题
对每一个子目录，执行相同的统计。
终止条件
遇到文件返回大小；空目录返回 0。
返回与合并
把所有孩子返回的大小相加。
实际边界
要处理权限错误、超深目录和符号链接形成的环。

真实查询 · PostgreSQL 递归 CTE

一辆自行车，需要多少个底层零件？

制造业的物料清单（BOM）把产品拆为组件、子组件和零件。PostgreSQL 官方文档就用“展开产品全部子零件”解释递归查询，并沿层级相乘、最终汇总数量。[5]

同类子问题
继续展开当前组件包含的子组件。
终止条件
没有子组件：到达最底层零件。
返回与合并
每条路径上数量相乘；同种零件的数量再相加。
实际边界
共享子件要按路径计量；循环依赖要检测并拒绝。

真实数据结构 · 浏览器 DOM

网页里套着的网页元素，也是一棵树。

一篇文章含章节，章节含小节；HTML 元素也可以包含更多元素。DOM 用树表示网页，递归遍历可以帮助提取内容或检查一棵子树。MDN 文档介绍了 DOM 的节点树结构。[6]

同类子问题
对当前元素的每个子元素重复遍历。
终止条件
没有子元素时，不再发起新的调用。
返回与合并
本元素计 1，再累加子树的元素数量。
实际边界
这里只数元素节点；文本和注释不在 children 中。

function count(el) {
  let total = 1;
  for (const child of el.children) {
    total += count(child);
  }
  return total;
}
函数会把每个子树的结果向上返回。
展开实际场景代码：递归统计教学目录对象（Python，可运行）
def total_kb(node):
    if isinstance(node, int):       # 文件：直接返回大小
        return node
    total = 0                      # 目录：累加子节点的结果
    for child in node.values():
        total += total_kb(child)
    return total                   # 空目录自然返回 0

project = {
    "说明.txt": 2,
    "设计": {"原型.png": 120, "图标.svg": 18},
    "文档": {"需求.pdf": 60},
}
print(total_kb(project))            # 200（KB，示例单位）

01 / 03

容易卡住的三个地方

为什么不是先把最大的圆盘移到终点？

它被上面的 n−1 枚圆盘挡住了，而且目标柱上不能有更小的圆盘。因此必须先完成一个“把小塔搬到辅助柱”的子问题。顺序来自问题约束，不是递归语法的规定。

递归一定比循环好？用缓存能省掉汉诺塔的搬运吗？

不一定。递归适合自然包含同类子问题的结构；过深的调用可能耗尽调用栈，也可以改用显式栈或循环。在标准三柱汉诺塔中，如果要实际输出全部动作，就必须完成 2ⁿ−1 次移动；缓存不能省略这些必要动作。只求“次数”时，可以直接计算公式，无需生成过程。

递归调用树很大，为什么调用栈只有 O(n)？

调用树描述整个执行过程发生过的所有调用；调用栈只保存当前还没有返回的那些调用。顺序执行时，左边的子问题完成、退栈以后，才进入右边的子问题。最深同时保留 n 层，而不是把整棵调用树都压入栈中。
